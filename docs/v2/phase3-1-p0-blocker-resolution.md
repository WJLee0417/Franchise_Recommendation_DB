# Phase 3-1 — 우선순위 1→2→3 정책 결정 및 조치 기록

## 1. 개·폐업률 100% 초과: DDL 수정

- **원천 근거:** 사용자 제공 2022Q1~2023Q2 서울 점포 CSV 457,043행 전수 확인.
- 개업률 >100: 5행; 폐업률 >100: 124행; **교집합 1행, 합집합 128행**. 폐업률 최댓값 4800%. 이전 원본 검증 문서의 '129개'는 두 지표의 단순 합계(5+124)이므로 '영향 행 129개'로 해석하면 안 된다.
- 공식 통계 정의는 서울시 상권분석서비스의 점포 산출 지표를 참고하지만, *이 파일과 같은 버전의 폐업률 분모 및 예외 처리 세부산식은 공개 설명만으로 확정할 수 없었다.* 따라서 >100 자체를 잘못된 값으로 판정할 근거는 불충분하다.
- **확정 데이터 보존 정책:** STORE의 `개업_율`, `폐업_률`을 원문 그대로 SRC에 보존하고, FACT에서 **비음수만 CHECK**. >100은 데이터 품질 경고/산식 분석 대상이며 무조건 clipping, 0 대체, 제거 금지.
- 신규 마이그레이션: `sql/v2/migrations/004_store_rate_nonnegative.sql`. 기존 `001_schema.sql`는 수정을 피하고 비파괴 ALTER로 변경; 향후 신규 DB는 P0 DDL 직후 적용. 실행 환경에서 기존 데이터가 0 미만 비율을 포함하면 적용 실패하도록 의도.
- P0 smoke 테스트 변경: -1 개업률의 MySQL CHECK 오류번호 3819 검증, 개업률 200·폐업률 4800 값 허용 확인, 관측기간 NOT NULL 등 기존 검사 유지. CI는 P0 생성→마이그레이션→P0 smoke→P1→P2 실행.

## 2. AREA 기준기간 없음: 유효기간·공간 버전 정책

### 데이터에서 확인된 사실
- 과거 AREA CSV (11열, 1,650행)는 `기준_년분기_코드`, 유효시작일, 유효종료일, version/date 또는 GeoJSON 경계 도형 필드 **모두 없음**.
- 좌표 2개와 면적은 경계 polygon 자체가 아니므로 두 스냅샷의 공간 일치/경계 변경을 보증할 수 없음.
- 서울 열린데이터광장은 **2024년부터 표준단위구역으로 공간 단위 변경**이라고 알림(매출 공개 기준 변경 안내에도 명시). 해당 설명만으로 과거 상권 파일의 유효시작일을 2022-01-01로 지정할 수 없음. 

### 확정 운영 정책
1. **SRC_SEOUL_AREA 적재는 허용**: 원본 CSV에 없는 기준일을 강제로 넣지 않음. `collection_batch_id`, 원본 파일 해시 및 수집 일시를 보존. 파일의 2023년 작성 경로/이름을 관측 기간으로 사용하지 않음.
2. **DIM_AREA 생성은 증빙 기반 허용**: 배포 기준일/공간 버전/경계 유효구간을 입증하는 공식 메타데이터 또는 적절한 변경 이력 매핑을 받기 전 **유효기간을 추정해 설정하지 않음**. `effective_start_date`는 필수이므로 검증 실패 레코드를 보류 대상으로 관리. 현재 아카이브 AREA 1,650건만으로 곧바로 DIM에 삽입하지 않는다.
3. **SCD2 business key**: `(area_code, source_area_version)`의 명세를 우선 확정. `source_area_version`은 원천 출처/경계버전으로 채우되 데이터에 없으면 임의 '2023' 등 생성 금지. `version_no`는 ETL이 검증된 도형·설명 변경 감지 후 순차 발급.
4. **시간 범위**: 유효시작일 포함, 종료일 미포함 (`[start,end)`). 구간 중복 금지 및 현재버전 한 건 규칙은 ETL의 트랜잭션으로 검증. 2024년 전후 키가 동일해도 경계를 동일하다고 가정하지 않는다.
5. **기간 기반 FACT 결합**: `period_key`가 가리키는 기준분기가 해당 `DIM_AREA` 버전의 유효구간과 합치하는지 확인 후 연결. 공간 버전 근거가 없으면 FACT 적재/비교는 보류하고 SRC 데이터만 유지.
6. **분석 보고**: 2022~2023과 2024 이후를 동질 공간 비교로 연결하지 않고, 별도 구간으로 분석하거나 정식 경계 크로스워크/가중 재배분 확보 후 검증한다.

## 3. 당월_매출_금액: 분기 지표로 해석

### 공식 근거와 원본 검증
- 서울 열린데이터광장 `OA-15572`은 **추정매출(상권)**, 단위 **원**, `STDR_YYQU_CD`=`기준_년분기_코드`, `THSMON_SELNG_AMT`=`당월_매출_금액` 필드를 공개한다.
- 같은 공식 데이터셋 FAQ에서 해당 지표를 **분기당 매출 금액 / 분기 총 매출액**이라고 설명하고, 성별/연령별 합계가 다를 수 있는 것은 개인+법인 매출 포함 때문이라고 명시한다.
- 보관본 125,692행을 검증한 결과 `당월_매출_금액 = 주중_매출_금액 + 주말_매출_금액` 및 요일별 7개 금액 합계가 **모든 행에서 일치**. 이 합계 정합성이 월/분기 단위를 독립적으로 증명하지는 않으며 공식 FAQ와 함께 해석한다.
- **결정:** 해당 공식 데이터셋과 동형의 역사적 `당월_매출_금액`은 **분기 기준 추정매출액(원)** 지표로 취급. 컬럼 문자열만 보고 월매출 또는 '월평균'으로 가정하지 않는다.
- **금지:** 원본 지표에 3을 곱해 임의로 분기화하거나 3으로 나누어 월평균 수치로 FACT 저장하지 않는다. 월평균 표현은 별도 derived metric로 명명·정의·검증 후 제공.
- DIM_PERIOD는 원본 코드 `20221`→`2022Q1` 등으로 정규화하고 3개월 시작/종료일을 명시; 정상적인 5자리 YYYYQ 패턴만 수용.
- API/신규 파일의 같은 이름이 **같은 산식/범위**를 보장하지 않으므로 버전별 소스 메타데이터/샘플 비교는 별도 Phase 3 검증.

### 기술 부채
- 현재 SRC_SEOUL_SALES에는 총액만 구조화되어 있고 `당월_매출_건수`와 요일별/연령별 구성 수치는 raw_record_text에만 있다. 세부 통계 분석 시 스키마 보강 필요.
- 현재 `FACT_AREA_SALES.estimated_sales_amount`는 의미가 포괄적이므로 데이터 카탈로그에 **분기 추정매출액(원)**으로 명시한다.
