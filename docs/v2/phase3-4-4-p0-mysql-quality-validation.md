## 환경과 범위

2026-10-29, MySQL 8.0.46 컨테이너 `franchise-phase3-original-mysql`, Python 3.12.14, PyMySQL 1.2.3을 사용했다. 중지된 기존 컨테이너를 시작했으며 스키마나 SRC를 초기화하지 않았다. 최초 확인 시 기존 49개 기본 테이블과 28개 DIM·FACT 테이블이 존재했고, 후자는 모두 비어 있었다. 기존 `ck_fast_open`, `ck_fast_close`는 음수만 제한했다. 정제 객체가 없는 것을 확인하고 마이그레이션 005를 한 번 적용했다. 생성된 두 테이블과 quarantine 뷰, 두 eligibility 차단 CHECK를 확인했다.

## 발견한 오류와 조치

기존 검증기는 먼저 연 읽기 트랜잭션이 MySQL의 기본 REPEATABLE READ 스냅샷을 유지해 별도 연결의 정제 커밋을 보지 못할 수 있었다. 최초 실행과 재실행 후 검증 연결을 커밋해 최신 결과를 보도록 수정했다. `--verify-only`에서 소스별 보고서가 초기화되지 않는 오류도 수정했고 회귀 테스트를 추가했다. 판정 규칙이나 원본 데이터를 기대값에 맞춰 변경하지 않았다.

### PR #5 후속 검토: 정책 변경 감지

기존 변환기는 정책 파일을 읽지 않아 JSON만 변경해도 처리했다. 수정된 변환기는 정책 JSON을 파싱하고 키 순서를 정렬한 UTF-8 정규화 내용의 SHA-256을 승인된 버전 `0.1.0` 및 구현의 고정 지문 `c517e44c856fe0ca99b563fff3fb54a58dffb10fdbf380e08384be529f6fd15c`와 비교한다. 정책 내용이나 버전 변경, 누락·잘못된 JSON·중복 키·비표준 숫자는 DB 연결 전 실패한다. JSON 공백·들여쓰기·객체 키 순서와 줄바꿈 차이는 의미 변경이 아니므로 허용한다. 실행 중에는 각 청크 커밋 전과 성공 기록 전에 다시 검사한다. 변경 시 현재 청크는 롤백하고 실행을 FAILED로 기록하며 이미 커밋한 청크는 유지한다. 승인된 원래 정책으로 복구하면 재개할 수 있다.

JSON은 여전히 정책 문서이며 판정 로직을 동적으로 실행하지 않는다. 새 정책의 적용은 판정 구현과 영향 범위 검토, 새로운 정책 버전 및 승인 지문 갱신, 기존 STG의 버전별 재처리 방안이 필요하다. 이 안전 장치는 변경된 정책을 자동 승인하지 않으며, 파일시스템 변경을 트랜잭션으로 잠그는 기능은 아니다. 검사 사이에 발생했다가 복구되는 일시적 변경은 감지할 수 없다.

실제 AREA 1,650행에서 임시로 변경한 정책을 사용하면 DB 연결 전 차단되어 실행 이력과 STG에 변화가 없었고, 원래 정책의 재실행 후에는 STG 전체 컬럼 및 `written_at` 지문이 동일했다. 별도 합성 MySQL에서는 같은 버전의 내용 변경, 버전 변경, 처리 중 정책 변경과 롤백·복구·재실행을 확인했다. 임시 파일을 사용했으며 실제 정책 파일과 원본 데이터는 변경하지 않았다. 변경된 구현으로 실제 584,385행을 읽기 전용으로 다시 전수 비교해 판정·이슈·기존 결과 해시가 모두 일치했다. Python 단위 테스트 18개와 별도 MySQL 정제 통합 시험도 통과했다. 결과는 `data/local/phase344_policy_real_smoke.json`, `data/local/phase344_policy_verify.json`에 보관한다. 정책 수정 후 실제 전체 배치를 다시 쓰기 모드로 재실행한 것은 아니며, 재실행 실측 범위는 AREA 1,650행과 합성 데이터다.

재실행 검증 지문도 기존의 행 ID·결과 SHA-256·`written_at` 세 필드에서 STG의 모든 컬럼으로 확장했다. 위 본문에 기록된 최초 전수 실행 시의 기존 지문은 당시 실제로 사용한 세 필드 기준이며, 후속 검증의 전체 컬럼 지문과 구분해야 한다.

최종 검토에서 SQL의 암묵적 숫자 변환으로 잘못된 STG JSON 값이 0과 일치할 가능성을 발견해, 비교 전에 저장된 값의 JSON 타입·숫자 형식·정밀도를 확인하도록 수정했다. 합성 MySQL에서 원본 값이 0일 때 STG 값이 JSON null, 누락, 비숫자 문자열이면 모두 실패하고, 정상 `UNSIGNED INTEGER` 대형 매출액은 통과하는 것을 확인했다. 보완된 SQL로 실제 584,385행을 다시 대조해 불일치 0건을 확인했다. 결과는 `data/local/phase344_final_sql_validation.json`에 보관한다.

## 검증 방법과 제한

`scripts/verify_p0_quality_mysql.py`는 각 원본 배치의 행 수와 경로 유일성을 확인하고, SRC에서 `evaluate()`를 다시 실행해 STG의 모든 필드, 이슈 코드, 원문·결과 해시 및 적재 차단 플래그를 행별로 비교한다. 동일 코드로 재평가하므로 이는 **저장 및 재현의 전수 검증**이며, 판정 알고리즘의 독립적인 정확성 증명은 아니다. 별도 오프라인 판정 분포와도 비교한다. 재실행 전후의 행 ID·결과 해시·`written_at` 지문을 비교한다.

`scripts/verify_p0_quality_sql.py`는 별도 SQL 식으로 원문 SHA-256, 식별 코드, 기간, 주요 숫자와 차단 플래그를 재확인한다. 숫자 비교는 원본의 형식과 정밀도가 `DECIMAL(65,10)`에 들어가는지 먼저 검사하며, 이 검사는 이슈 코드 판정 전체를 독립적으로 재구현하지는 않는다.

실행 전후 SRC 전체 컬럼을 `source_row_id` 순서로 직렬화한 SHA-256을 비교하고, 28개 DIM·FACT의 행 수를 비교한다. DIM·FACT가 모두 비어 있으면 행 수 비교가 내용 보존을 입증한다. 로컬 결과 JSON은 `data/local/`에만 보관하며 원본 행이나 접속정보는 커밋하지 않는다.

## 회귀 및 복구 시험

Python 단위 테스트 14개가 통과했다. 이 중 두 개는 검증 스크립트의 트랜잭션 갱신과 `--verify-only` 보고서 생성을 검사한다. 별도의 합성 MySQL 8 컨테이너에서 기존 수집 및 정제 통합 시험과 P0·P1·P2 스키마 무결성 시험을 실행했다. 별도 5행 AREA 합성 배치의 두 번째 데이터 청크 커밋에 실패를 주입했을 때 최초 2행만 유지되고 해당 실행이 FAILED로 기록됐다. 재실행해 전체 5행을 확보했고, 합성 SRC 원문 또는 규칙 버전 변경 후 재실행은 기존 결과 차이를 감지해 실패했으며 STG 결과 해시와 `written_at`은 변하지 않았다. 실제 원본 처리 중 강제 종료한 시험은 아니다.

## Phase 3-5 전제

AREA 공식 유효기간과 공간 버전이 없고, 교차 소스 업무키 및 업종 분류 매핑 정책은 완성되지 않았다. ACCEPT를 포함한 모든 STG 행의 `dim_area_eligible`과 `fact_eligible`은 0이다. DIM·FACT 적재 또는 임의 날짜 생성은 수행하지 않는다.
